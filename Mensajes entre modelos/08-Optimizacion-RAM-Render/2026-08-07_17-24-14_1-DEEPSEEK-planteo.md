# Planteo: Estrategia G (Chrome real + scroll infinito IG) muere por OOM en el free de Render (512 MB)

## Contexto del proyecto
- App de sorteos con extracción de comentarios de Instagram. Pipeline: G → A → B → C → F → D.
- **Estrategia G** = "Scroll anónimo completo": lanza Chrome real (visible/PVR) y hace scroll infinito del modal de comentarios para capturar participantes sin sesión. Es la estrategia #1 que resuelve ~144/152 en un post de prueba chico y ~2393/2398 en un post grande.
- Backend Node+Express+Prisma desplegado en **Render plan free (512 MB)**, Docker con Playwright + Chrome real + Xvfb.
- **Objetivo del hilo:** que la Estrategia G corra DENTRO de los 512 MB del free. Si no, pasar a Chrome headless embebido (opción en curso), Apify, o pedir plan pago.

## 2. Diagnóstico ya hecho (razones por las que muere)

**El contenedor ya arranca al límite.** Con Chrome real (visible o headless vía `CHROME_MODE=headless`) el contenedor consume:

| Estado | `usadoMb`/`limiteMb` al `MEM: inicio recolección` | Margen |
|---|---|---|
| Visible + flags + bloqueo imágenes | 484/512 | 28 MB |
| **Headless (CHROME_MODE=headless, sin Xvfb)** | **477/512** | **35 MB** |

- La medida se hace con `/sys/fs/cgroup/memory.current` / `memory.max` (cgroup v2) — ver `api/src/lib/memoria.ts`.
- Eventos Render: `server_failed` con `nonZeroExit:137` (SIGKILL, = OOM killer). Ocurre a los ~82-85 segundos de iniciado el POST `/api/sorteos/analizar`. El request muere con 502.
- El scroll infinito agrega el pico final encima de los ~477 MB de boot → cruza 512 → OOM.
- **Datos clave:** los micro-ahorros ya probados mueven 7-35 MB (necesitamos >100 MB de margen):
  - Bloqueo de imágenes/media/font: ahorra ~28 MB (484→~484... en realidad evitó subir más; el boot quedó 484 con el resto).
  - Headless sin Xvfb: ahorró solo ~7 MB (477 vs 484). El Chrome headless moderno casi no ahorra porque igual renderiza páginas.
  - Flags: `--no-zygote`, `--js-flags=--max-old-space-size=384`, `--expose-gc`, `--disable-software-rasterizer`, `--disable-features=TranslateUI,VizDisplayCompositor`, viewport 1280x720. `--single-process` **crashea** (navegador DISCONNECTED).
- En **local (Windows, sin cgroup)** el `MEM:` no refleja el contenedor (`usadoMb/limiteMb=0`); el rss de Node es ~140 MB. Solo sirve para captura.

## 3. Opciones sobre la mesa

1. **Render Standard (USD 25/mes, 2 GB):** definitivo, pero paga. Starter (7/mes, 512 MB) NO alcanza.
2. **Chromium headless embebido** en vez de Chrome real para el caso anónimo: ahorro estimado 50-80 MB. Riesgo: IG detecta Chromium de Playwright y corta (históricamente capturó ~596/2538 vs 2393 con Chrome real). Para posts CHICOS (~150-300) pasó localmente bien: 144/152.
3. **Apify** (token en env, crédito free mensual): fuente primaria sin sesión; Chrome real solo si falla.

## 4. Restricciones y decisiones tomadas

- Backup del código vigente ya guardado en `Obsoletos/10-Optimizacion-RAM-2026-08-07_15-40-22/` (instagram-v2.ts, scroll-anon-completo.ts, Dockerfile) y commiteado.
- No romper el flujo local/visible de la Estrategia G (99.2% de comentarios → esto se verifica con Chrome real visible). El cambio es SOLO para el flujo anónimo (sin cookies ni sesión guardada).
- El reciclado de página cada 40 iteraciones NO se dispara en posts chicos (las iteraciones = `Math.min(300, Math.max(40, ceil(esperado/15)))` y el check es `i>0 && i%40===0` → 0..39).
- Headless nuevo de Chrome (channel:'chrome', headless:true) NO PCM se detecta peor que Chromium embebido.
- Implementación actual en `api/src/collectors/instagram-v2.ts` líneas ~100-120: `const headless = !!cookieStr || process.env.CHROME_MODE === 'headless'`.
- Si se usa `channel: undefined` (Chromium Playwright puro) → el fallback se maneja: con headless SI falla channel chrome → tira error "No se pudo lanzar el navegador".
